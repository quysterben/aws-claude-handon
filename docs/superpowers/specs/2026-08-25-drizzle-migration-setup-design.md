# Drizzle Migration Setup — Design

**Status:** Approved by user, ready for implementation planning.

## Goal

Add Drizzle ORM + `drizzle-kit` to `app/api` so schema migrations can be generated and applied against a local Postgres database, run manually from a developer machine. This is dev tooling only — no Lambda handler or CDK stack changes. Runtime DB integration (Lambda connecting to Postgres) is explicitly out of scope and will be a separate future task.

## Context

- `app/api` currently has no database layer at all — only a single `GET /health` Lambda route (see `CLAUDE.md`).
- The repo root has an (as yet uncommitted) `docker-compose.yaml` that provisions local Postgres 16:
  ```yaml
  services:
    db:
      image: postgres:16
      environment:
        POSTGRES_USER: postgres
        POSTGRES_PASSWORD: postgres
        POSTGRES_DB: app
      ports:
        - 5432:5432
  ```
- `app/api` is a Yarn Berry (`node-modules` linker) project; installs must use `yarn add`, not `npm`.

## Decisions

- **Driver:** `postgres` (postgres-js) — Drizzle's recommended lightweight Postgres driver, used by `drizzle-kit` to connect for `generate`/`migrate`. Chosen over `pg` (node-postgres) for simplicity and because it's the more natural fit if Lambda runtime integration is added later.
- **Migration flow:** Manual, local-only for now. Developer runs `docker compose up -d` (repo root) to start Postgres, then `yarn db:generate` / `yarn db:migrate` from `app/api/`. No auto-migration on Lambda cold start, no CDK custom resource / pipeline step — both are unnecessary complexity while there is no real RDS instance provisioned.
- **Schema scope:** Scaffolding only. `db/schema.ts` starts empty (no tables). The developer adds real tables afterward; this task only proves the generate/migrate wiring works.

## Dependencies

Added via `yarn add` (regular deps) and `yarn add -D` (dev deps) from `app/api/`:

- `drizzle-orm` (dependency) — schema definition and types
- `postgres` (dependency) — postgres-js driver
- `drizzle-kit` (devDependency) — CLI for `generate` / `migrate` / `studio`

## File layout

New files under `app/api/`:

- `db/schema.ts` — empty schema scaffold (no tables yet; ready for future `pgTable(...)` definitions)
- `db/migrations/` — output directory for SQL migration files generated by `drizzle-kit generate` (created on first run)
- `drizzle.config.ts` — drizzle-kit config:
  - `dialect: "postgresql"`
  - `schema: "./db/schema.ts"`
  - `out: "./db/migrations"`
  - `dbCredentials.url` sourced from `process.env.DATABASE_URL`
- `.env.example` — documents the expected shape:
  ```
  DATABASE_URL=postgres://postgres:postgres@localhost:5432/app
  ```
  (matches the root `docker-compose.yaml` credentials)
- `.env` — actual local value, gitignored, not committed

Modified files:

- `app/api/.gitignore` — ensure `.env` is excluded (verify not already covered by an existing pattern)
- `app/api/package.json` — add scripts:
  - `db:generate`: `drizzle-kit generate`
  - `db:migrate`: `drizzle-kit migrate`
  - `db:studio`: `drizzle-kit studio`

## Env loading

Recent `drizzle-kit` versions load `.env` from the working directory automatically, so no extra `dotenv` dependency should be needed. Verify this during implementation; if `drizzle.config.ts` can't see `DATABASE_URL` without it, add `dotenv` as a devDependency and `import "dotenv/config"` at the top of `drizzle.config.ts`.

## Testing / verification

Since no tables are added in this task, `yarn db:generate` may produce no migration file (empty schema diff) — that's expected, not a failure. Verification is limited to proving the wiring is correct, not a full apply-migration round trip:

1. `docker compose up -d` (repo root) — local Postgres reachable on `localhost:5432`
2. From `app/api/`: `yarn db:generate` — exits 0, no config/connection errors
3. From `app/api/`: `yarn db:migrate` — exits 0, no config/connection errors (applies zero migrations)
4. Existing `yarn build`, `yarn test`, `yarn cdk synth` still pass (this task must not break the existing CDK scaffold)

A full generate → migrate → apply round trip against a real table is deferred until the developer adds their first schema table — out of scope here.

## Out of scope

- Lambda runtime DB connection code (no handler imports `drizzle-orm`/`postgres` yet)
- CDK changes (no RDS/Aurora provisioning, no VPC, no secrets manager wiring)
- Auto-migration on deploy or cold start
- Any real table/schema definitions beyond the empty scaffold
